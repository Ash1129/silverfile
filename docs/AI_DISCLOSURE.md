# AI disclosure

## In the product

SilverFile calls three Claude models at runtime when an API key is present, and none of them otherwise:

| Step | Model | Input | Output | What it cannot do |
| --- | --- | --- | --- | --- |
| Intake answer parsing | claude-haiku-5-5 | The current question, the taxpayer's reply and the slot list | Slot updates as JSON | Produce a number that reaches a line; the slots are facts (names, dates, yes/no, declared document types, a stated estimated-payment amount that is then recorded as `user_input` provenance) |
| Document extraction | claude-sonnet-5-5 | One document image and the schema for the declared form type | Typed fields, a per-document confidence, an issues list | Decide what a field means; every field is checked by Eligibility and used only through `tax_math` |
| Review | claude-opus-5-5 | Lines, provenance, extracted documents, the firm's draft rules | Findings with severity and a target agent | Change a number; it may only send work back |

The orchestrator, eligibility, computation, the escalation gate and the `tax_math` tool server are deterministic code. Every value on the draft form is the return value of a `tax_math` tool call or a fact the taxpayer typed, and the provenance record says which.

Prompts are in `src/silverfile/agents/*.py` next to the code that uses them. Token counts per model call are recorded in the return state (`token_log`) and shown on the dashboard.

Without `ANTHROPIC_API_KEY` the system runs offline with a scripted intake parser, sidecar JSON for document images and rule-only review, which is how the test suite runs. On a copy with no server key, any visitor can paste their own key into the header's "API key" control to run the models on it for their browser session (held only in the server's memory, never saved); `SILVERFILE_REQUIRE_KEY=1` makes that key mandatory before any page (see `src/silverfile/dashboard/gate.py`).

## In the making of it

The design stage used Blueprint (the course's agent-architecture tool), which calls Claude for its interview, design, kit and tailoring steps; its full output is in `docs/blueprint/`.

The code, tests, fixtures and documents in this repository were written with Claude (Claude Code) working from the brief, with the author directing the work, choosing the architecture questions to settle, reviewing the runs and the outputs, and deciding what to keep. The synthetic documents and images were generated by a script in this repository, not by a model. The measurements in `docs/metrics.md` and the traces in `traces/` are from real runs on the dates they record.

### Guardrails B (Gabriel Maurad)

I used Claude, in a chat with access to the repository, for my focus area, which was dignity and intake safety. I asked it to read the assignment brief, our team plan and the existing intake code, and to check the intake against the brief's dignity rules (§4.3) and the third-party escalation condition (§4.4, condition 6). It ran sample answers through the intake's detection rules and found six gaps. The worst was that a married taxpayer saying "My wife is Mary Whitfield" was flagged as possible elder exploitation. Claude drafted the fixes in `src/silverfile/agents/intake.py`, the 29 tests in `tests/test_intake_dignity.py`, the design note `docs/INTAKE_DIGNITY.md`, the policy text in `data/policy.md`, and the conversation walkthrough in `demo/eval_case_1.md`. I reviewed every change in VS Code's side-by-side view, asked for corrections where its wording or my pull-request description was inaccurate, ran the full test suite on my own machine (371 passed) and made the commits myself. Some of the proposed behavior choices were created by Claude and reviewed and accepted by me. For example, some of the passed reviews were that a helper who states a power of attorney is noted for the preparer rather than pausing the return, and that a single filer is asked for only one Social Security number.

No real taxpayer data was used at any point. All SSNs are in the 900 test series.

## Codex-assisted HITL revision

The explicit blocking-review, human-edit completion, deterministic continuation check and unknown-fact controls were implemented with Codex from the human-specified requirements. Verification used the offline pytest suite, ten existing evaluation cases, a bounded long-note transfer check and synthetic preview data. The working files, environments and validation logs are kept in the Git-ignored `agent_workspace/` directory. No real taxpayer data was used, and no commit was created by the agent.
